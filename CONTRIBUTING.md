## Code of conduct

Be respectful and constructive. Harassment, discrimination and personal attacks are not tolerated. Give feedback on the code, not the person, and assume good intent. Maintainers may remove comments or contributions that break these rules.

## Getting started

Prerequisites: Bun, pnpm, .NET SDK, PostgreSQL (or Docker, see `docker-compose.yml`).

```bash
pnpm install
pnpm db:push
pnpm dev
```

Useful commands:

| Command | Purpose |
| --- | --- |
| `pnpm dev` | Start the development server |
| `pnpm build` | Build for production |
| `pnpm test` | Run tests (vitest) |
| `pnpm db:push` | Push the database schema |
| `pnpm db:studio` | Open the database UI |

Run the tests before pushing. Biome (lint + format) runs automatically on staged files of `apps/web` and `apps/mobile` at each commit (husky pre-commit hook); run it on everything with `pnpm lint`.

## Workflow

1. Pick or create an issue.
2. Create a branch from `develop` following the [branch naming](#branch-naming) rules.
3. Commit following the [commit convention](#committing-changes).
4. Open a pull request targeting `develop`. Releases are a pull request from `develop` to `main`.
5. Get one approval and a green CI, then merge.

## Branch naming

We use [Conventional Branch](https://conventional-branch.github.io/): `<type>/<short-description>`, in lowercase with hyphens.

Types: `feat`, `fix`, `chore`, `docs`, `refactor`, `test`, `ci`.

Examples:

- `feat/login-page`
- `fix/db-timeout`
- `docs/contributing`

## Committing changes

Commit messages follow [Conventional Commits](https://www.conventionalcommits.org/) so that changelogs can be generated automatically.

```
<type>(<optional scope>): <description>
```

Examples:

- `feat(web): add login page`
- `fix(server): handle database timeout`
- `docs: add contributing guide`

Keep the description short, in the imperative mood, and without a trailing period.

A husky `commit-msg` hook (commitlint) rejects messages that do not follow this format.

The version is computed from these commits when `develop` is merged into `main` ([git-cliff](https://git-cliff.org), `cliff.toml`):

- `fix:` (and any other type) bumps the patch: `1.4.2` → `1.4.3`
- `feat:` bumps the minor: `1.4.2` → `1.5.0`
- `feat!:` or a `BREAKING CHANGE:` footer bumps the major: `1.4.2` → `2.0.0`

The release creates the `vX.Y.Z` tag, a GitHub Release with the changelog, and the Docker images `X.Y.Z`, `X.Y`, `sha-<commit>` and `latest` on GHCR. Preview the changelog locally with `pnpm changelog`.

## Pull request guidelines

- Target the `develop` branch.
- Link the related issue (e.g. `Closes #12`).
- Describe what changed and why; add screenshots for UI changes.
- Make sure all tests and CI checks are green before merging.
- Keep PRs focused and reasonably small.
- Pull requests are merged with a **merge commit**.

## Reviewing code

- Every PR needs **at least 1 approval** before merging.
- If a PR changes both the front end (`apps/web`, `apps/native`) and the back end (`apps/server`), it must be validated by **both a front-end dev and a back-end dev**.
- The author cannot approve their own PR.
- Reviewers check correctness, readability, tests, and compliance with the conventions above.
- Resolve all review comments before merging.

## API documentation

The API is documented automatically with Swagger / OpenAPI, generated by the .NET backend (`apps/server`) and served at `/swagger` when the server runs locally. Keep endpoints annotated (summaries, response types) so the documentation stays accurate.
